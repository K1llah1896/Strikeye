# 设计

## 决策

**每场一个目录**：单场模式所有文件平铺在目标目录里，批量模式如果沿用会把 N 场的 `match_<id>_players.csv` 堆在一起——虽然文件名带 id 不冲突，但 `xlsx`/`html` 里内嵌了相对资源引用，目录隔离最省事，也便于整目录打包。

**失败隔离**：用户批量导出的常见失败是某场缺 kill_context（没跑过 `killctx --store`）或库已损坏。一场坏掉就整批回滚会让"导出 20 场"变成不可用，所以逐场记错、最后汇总，只有 0 场成功才返回错误（退出码非 0）。

**过滤在 Go 侧做而不是 SQL**：`Demos().List` 已经返回全部字段，过滤条件只有三个、量级是几千行，没必要新增查询方法；`--limit` 在遍历时截断，保证顺序稳定（按 id 升序）。

**索引文件原子写**：`export_index.json` 用 `.part` → rename，与仓库其他产物一致，避免半截 JSON 被脚本读到。

## 已知取舍

- 只导出 `parse_status=parsed` 的比赛（`BatchFilter.ParsedOnly` 默认为真）；想导未解析的场次需要先 `parse`。
- 不并发：一场导出约 20–80ms，几百场也在秒级，并发只会让 SQLite 连接与写文件竞争。
