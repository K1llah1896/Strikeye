# 设计

## 决策

**为什么用现有 demo 的队名做切换而不是全局队伍选择器**：分析师的会话上下文是"我正在看的这场"，队伍视角的首要问题是"这场里的队是什么水平"。全局选择器需要额外的队伍列表查询与持久化，收益低于把当前两队放在标签条上。CLI 仍保留 `--team` 任意队名入口。

**为什么把回放缓存加载下沉到 `internal/parser`**：CLI 与 UI 都需要"给定 demo 找出可用的 `.rpl` 并读出每回合"，旧实现散落在 `cmd/strikeye-cli/zones.go`（含 WSL↔Windows 路径回退）。下沉后只有一份实现，UI 不必复制粘贴，未来 `mapcontrol`/`zones` 也能复用。

**为什么分区块降级**：侦察报告需要回放缓存与 callout，档案与交手只需要 SQLite。把三者绑成一个失败会掩盖"其实有数据"的情况，因此逐块渲染、逐块提示。

**为什么标签页而不是把三块塞进概览页**：队伍视角是跨场次视图，与单场概览的时间尺度不同；塞进概览会让"这场怎么样"和"这支队怎么样"混在一起。

## 风险

- 队伍名依赖 demo 元数据：占位名（`Team A`/`Team B`）会让档案看起来像真实队伍。当前不做过滤，靠用户导入带元数据的 demo；后续可在 `.info` 缺失时提示。
- `tendency.Build` 会遍历所有已解析 demo 的回放缓存，首次打开标签页有秒级延迟；已放到后台 goroutine 并只跑一次（`teamSeq` 去重）。
